## 1. Scope and method

Reviewed:

- Spring Security configuration, JWT issuance/validation, authentication and account flows
- All 15 REST resources, the service/repository layers, and the role-scoping mechanism
- The Angular client's token handling and route guards
- Production deployment: `deploy/prod-server/compose.yml`, `ankobra-web.conf` (nginx), `.env.example`, `backup.sh`, jib image config
- Dependency posture (`npm audit`), CI gates (`.github/workflows/`)
- Live black-box probing of the production origin (unauthenticated only — no credentials were used, no data was written)

Not covered: penetration testing against an authenticated session (no non-admin production credentials were available), Java dependency CVE scanning (no scanner is wired into the build — see G-02), infrastructure outside this app's compose stack, and the shared `monitoring` network's other tenants.

**Important caveat on exploitability.** `DataSeeder` is `@Profile("dev")` (`DataSeeder.java:58`), so production currently seeds only the `admin` account. Every finding below that depends on a `ROLE_USER` (client) session is therefore **latent today and live the moment the first client login is created** — which is the portal's entire purpose. They are rated on the impact they will have when that happens, not on today's zero-client state. Do not read the current absence of client accounts as mitigation.

### The subdomain inventory, and why decision 4 is a judgement call

The 2026-08-06 note said `includeSubDomains` was omitted because the host "also serves
`web.`/`portainer.`/`monitoring.` from another config". Enumerating `server_name` across
`/etc/nginx/sites-enabled/` shows that was an undercount — there are **seven** `jojoaddison.net`
subdomains, not three:

| Host | HTTPS | HTTP | Notes |
|---|---|---|---|
| `docker.` | 403 | 301 → HTTPS | Docker registry; TLS valid |
| `kojo.` | 200 | 301 → HTTPS | TLS valid |
| `monitoring.` | 302 → `/login` | 301 → HTTPS | TLS valid |
| `ndua.` | 502 | 301 → HTTPS | Upstream down, but TLS valid and the redirect is correct |
| `portainer.` | 200 | 301 → HTTPS | TLS valid |
| `web.` | 301 → apex | 301 → HTTPS | TLS valid |
| `dev.` | **no answer** | **no answer** | **Resolves to `46.124.145.61` — a different machine entirely, not this server. Answers on neither port 80 nor 443.** |

Six of seven pass cleanly: valid certificates, and every one redirects HTTP to HTTPS already, so
`includeSubDomains` changes nothing for them. `dev.` is the exception and the reason this was
escalated rather than just done. It is not on this host, it is not reachable, and nobody here
controls what it becomes.

**Decision: enable anyway.** Nothing is broken today, because nothing answers. The accepted risk is
explicit: whoever brings `dev.jojoaddison.net` back must serve it over HTTPS, or it will be
unreachable in any browser that has visited the apex within the preceding year — and no header
change here can undo that for a browser that has already cached the assertion. That constraint
belongs in the runbook, not just in this table.

*Verification commands for all of the above are in the appendix.*

### Outcome

All six items shipped on 2026-08-24. `./mvnw verify` is green at **586 tests** (three new classes:
`BreachedPasswordCheckerTest`, `PasswordChangeRequiredIT`, `CsrfProtectionIT`), `npm test` at **131
files** with lint clean, and `npm audit --omit=dev` reports nothing.

Two things are worth carrying forward more than the tick-list:

- **The CSRF exemption.** Moving the token into a cookie and reading it back through a
  `BearerTokenResolver` disables CSRF protection for every authenticated request, because the resource
  server exempts anything its resolver can read a token from. The suite stayed green throughout,
  because tests that omit the CSRF token also omit the session cookie and so never enter the exempted
  state. Only a request against a running server showed it. Full write-up under SEC-06.
- **G-06 had already been done and was recorded as open.** A fixed finding that nobody writes down is
  indistinguishable from an unfixed one, and the next person pays for the difference.

**Not yet deployed.** The nginx `includeSubDomains` change needs `deploy.sh --with-nginx`; everything
else needs an application deploy. The cookie migration signs every existing session out on release —
old tokens live in `localStorage`, and nothing reads them any more.

### SEC-00 — Prod CORS blocked every POST *(fixed in `e7416a9`, awaiting deploy)*

Recorded for completeness since it was the trigger for this audit. `POST /api/authenticate` and `POST /api/public/enquiries` both returned `403 Invalid CORS request` in production. Fixed in `application-prod.yml`. **Still to do:** the fix is committed and pushed but *not deployed* — production is running the previous image and login is still broken. See §5, step 0.

### SEC-01 — No authorization on any write verb *(Critical)*

**Where:** `ProjectResource.java:72,94,128,216` · `TicketResource.java:72,94,128,216` · `ClientResource.java:72,94,128,211` — and by extension every other resource.

The three "scoped" resources apply `PortalSecurityService` on **read paths only**:

| Verb | Endpoint | Scoped? |
|---|---|---|
| `GET` | `/api/projects` | ✅ `ProjectResource.java:168` |
| `GET` | `/api/projects/{id}` | ✅ `ProjectResource.java:205` |
| `GET` | `/api/projects/count` | ❌ (SEC-03) |
| `POST` | `/api/projects` | ❌ **none** |
| `PUT` | `/api/projects/{id}` | ❌ **none** |
| `PATCH` | `/api/projects/{id}` | ❌ **none** |
| `DELETE` | `/api/projects/{id}` | ❌ **none** |

The delete handler in full (`ProjectResource.java:216-223`) contains no check of any kind:

```java
@DeleteMapping("/{id}")
public ResponseEntity<Void> deleteProject(@PathVariable("id") Long id) {
    LOG.debug("REST request to delete Project : {}", id);
    projectService.delete(id);
    return ResponseEntity.noContent()...
}
```

There is no compensating control further down: `grep` for `@Secured`/`@PreAuthorize`/`@PostAuthorize` across `service/` returns nothing, so `@EnableMethodSecurity(securedEnabled = true)` (`SecurityConfiguration.java:27`) is enabled but unused outside `UserResource` and `AuthorityResource`. The only gate these endpoints pass is `/api/** → authenticated` (`SecurityConfiguration.java:81`).

**Impact.** Any authenticated client (`ROLE_USER`) can:

- `DELETE /api/clients/{id}` — delete any other client, cascading to their projects, tickets and quotes
- `PUT /api/projects/{id}` — rewrite another client's budget, status, or reassign it to themselves
- `DELETE /api/tickets/{id}` — destroy another client's support history
- `POST /api/projects` with `client.id` set to anyone

This is destructive, cross-tenant, and requires nothing but a valid login and `curl`. The client-side `/cms` ADMIN route guard is not a control — it governs which UI renders, not which HTTP requests the server honours.

**Repro** (once a client account exists):

```bash
TOKEN=$(curl -s -X POST https://jojoaddison.net/api/authenticate \
  -H 'Content-Type: application/json' \
  -d '{"username":"<client-login>","password":"<pw>"}' | jq -r .id_token)

# Returns 404 — read scoping works.
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $TOKEN" \
  https://jojoaddison.net/api/projects/<other-clients-project-id>

# Returns 204 — the same object is deleted anyway.
curl -s -o /dev/null -w '%{http_code}\n' -X DELETE -H "Authorization: Bearer $TOKEN" \
  https://jojoaddison.net/api/projects/<other-clients-project-id>
```

The asymmetry between those two responses is the whole finding.

**Remediation.** Two layers; implement both.

*Layer 1 — coarse deny-by-default in `SecurityConfiguration`, so a newly generated resource is safe by default rather than open by default.* Insert **above** the `/api/**` rule:

```java
// CMS-managed reference data: staff only, all verbs.
.requestMatchers("/api/leads/**", "/api/service-items/**", "/api/courses/**",
                 "/api/team-members/**", "/api/milestones/**", "/api/quote-lines/**")
    .hasAnyAuthority(AuthoritiesConstants.ADMIN, AuthoritiesConstants.CONSULTANT)
// Client-facing entities: reads are scoped in the resource; writes are staff-only.
// Tickets are deliberately absent from these three lines — see the ticket policy below.
.requestMatchers(HttpMethod.POST,   "/api/projects/**", "/api/clients/**", "/api/quotes/**")
    .hasAnyAuthority(AuthoritiesConstants.ADMIN, AuthoritiesConstants.CONSULTANT)
.requestMatchers(HttpMethod.PUT,    "/api/projects/**", "/api/clients/**", "/api/quotes/**")
    .hasAnyAuthority(AuthoritiesConstants.ADMIN, AuthoritiesConstants.CONSULTANT)
.requestMatchers(HttpMethod.PATCH,  "/api/projects/**", "/api/clients/**", "/api/quotes/**")
    .hasAnyAuthority(AuthoritiesConstants.ADMIN, AuthoritiesConstants.CONSULTANT)
.requestMatchers(HttpMethod.DELETE, "/api/**")
    .hasAnyAuthority(AuthoritiesConstants.ADMIN, AuthoritiesConstants.CONSULTANT)
```

**Implementation note — `DELETE` landed as staff, not ADMIN-only.** This section first proposed `hasAuthority(ADMIN)` for every delete. It shipped as staff (ADMIN + CONSULTANT): the goal is to stop *clients* destroying other tenants' data, and consultants already hold full write access on everything they can delete, so ADMIN-only deletes buy little — while blocking consultants from routine delivery work, which in practice invites admin-account sharing. That is a worse outcome than the one it prevents.

**Ticket policy — decided 2026-08-05: clients do raise their own tickets.** So `/api/tickets` cannot take a blanket staff-only write gate and is the one entity that genuinely needs per-object checks. Per verb:

| Verb | `ROLE_USER` (client) | Rule |
|---|---|---|
| `POST /api/tickets` | ✅ allowed | The owning client is **forced server-side** to `requiredClientScope()` for non-staff — the submitted `client.id` is ignored, not validated. |
| `PUT` / `PATCH /api/tickets/{id}` | ✅ own tickets only | Check the **persisted** owner before the write, and reject any payload that changes `client`. |
| `DELETE /api/tickets/{id}` | ❌ | Covered by the blanket `DELETE → ADMIN` rule above. Clients close tickets; they do not delete support history. |

Forcing rather than validating the owner on `POST` is a deliberate choice, not a necessity: `TicketDTO.client` is `@NotNull` (`TicketDTO.java:41-42`) and `Ticket.client` is `@ManyToOne(optional = false)`, so a ticket with no client is already a 400 before any authorization runs, and a validating check would be correct today. Force anyway — it takes the tenant key out of the caller's hands entirely instead of checking what they sent, so the invariant survives someone later relaxing the constraint, adding a `PATCH` path that skips the check, or regenerating the DTO from JDL:

```java
if (!portalSecurity.isStaff()) {
    ClientDTO own = new ClientDTO();
    own.setId(portalSecurity.requiredClientScope());
    ticketDTO.setClient(own);          // overwrite whatever was submitted
}
```

Handle the `-1L` sentinel explicitly. A non-staff user with no linked `Client` would otherwise reach the database with `client_id = -1` and fail the foreign key, surfacing as a 500 rather than a 403 — the right failure direction but the wrong response and a noisy one. Reject it in the handler and assert that in a test.

Guarding re-parenting on `PUT`/`PATCH` is what stops the obvious escalation: a client who may edit their own ticket must not be able to move someone else's ticket onto their own client record, nor move theirs onto another's.

*Layer 2 — per-object ownership checks for anything a client may legitimately write.* Add to `PortalSecurityService`:

```java
/** Throws unless the current user may act on data belonging to {@code clientId}. */
public void assertCanAccessClient(Long clientId) {
    if (!canAccessClient(clientId)) {
        throw new AccessDeniedException("Not permitted for client " + clientId);
    }
}
```

and call it in each mutating handler *before* the write, resolving the owning client from the **persisted** entity (never from the request body, which the caller controls):

```java
@DeleteMapping("/{id}")
public ResponseEntity<Void> deleteTicket(@PathVariable("id") Long id) {
    ticketService.findOne(id).ifPresent(dto ->
        portalSecurity.assertCanAccessClient(dto.getClient() == null ? null : dto.getClient().getId()));
    ticketService.delete(id);
    ...
}
```

For `POST`, validate the *submitted* `client.id` against `canAccessClient` so a client cannot create records owned by someone else. For `PUT`/`PATCH`, check **both** the stored owner and the submitted owner, or a caller can re-parent a record they own onto another client.

### SEC-02 — Seven resources have no scoping at all *(Critical)*

**Where:** `QuoteResource.java` · `QuoteLineResource.java` · `MilestoneResource.java` · `LeadResource.java` · `CourseResource.java` · `ServiceItemResource.java` · `TeamMemberResource.java`

Only `ClientResource`, `TicketResource` and `ProjectResource` reference `PortalSecurityService`. The remaining seven are unmodified generated CRUD behind `/api/** → authenticated`. Every verb on every one of them is reachable by any authenticated user.

Worst cases:

- **`GET /api/leads`** (`LeadResource.java:144`) returns every marketing contact-form submission — name, email address and free-text message — to any logged-in client. These are third parties who submitted a form on a public website and have no relationship with the querying user. This is a personal-data disclosure with GDPR consequences, not just an access-control bug.
- **`DELETE /api/leads/{id}`** (`LeadResource.java:171`) lets any authenticated user destroy the sales pipeline.
- **`GET /api/quotes`** (`QuoteResource.java:150`) exposes commercial pricing, discounts and quote status across all clients — directly useful to a competitor holding any client login. Note `PortalSecurityService`'s own javadoc claims a client is restricted "transitively, only that client's projects, tickets **and quotes**" (`PortalSecurityService.java:12-14`); for quotes that is documented but never implemented.

**Remediation.** Layer 1 of SEC-01 closes the `Lead`/`ServiceItem`/`Course`/`TeamMember`/`Milestone`/`QuoteLine` surface outright (staff-only). `Quote` needs real scoping in `QuoteResource` mirroring `ProjectResource.java:160-210`, plus the `assertCanAccessClient` calls from SEC-01 Layer 2. Also correct or implement the `PortalSecurityService` javadoc so it stops describing a control that does not exist.

### SEC-03 — `/count` endpoints are an unscoped extraction oracle *(High)*

**Where:** `ProjectResource.java:185` · `TicketResource.java:185` · `ClientResource.java:185`

The list endpoints scope by overwriting `criteria` (`ProjectResource.java:167-172`). The sibling `/count` endpoints accept the same `Criteria` object and apply no scoping:

```java
@GetMapping("/count")
public ResponseEntity<Long> countProjects(ProjectCriteria criteria) {
    return ResponseEntity.ok().body(projectQueryService.countByCriteria(criteria));
}
```

JHipster criteria expose per-field operators (`equals`, `contains`, `greaterThan`, `in`, …) over every column. A client blocked from *reading* another client's projects can still ask questions about them and get truthful answers:

```
GET /api/projects/count?clientId.equals=7                    -> how many projects client 7 has
GET /api/projects/count?clientId.equals=7&budget.greaterThan=500000
GET /api/projects/count?clientId.equals=7&name.contains=acme
```

Binary-searching `budget.greaterThan` recovers exact figures; iterating `name.contains` over an alphabet recovers names character by character. This reduces SEC-01/02's list scoping to a speed bump for a determined caller, and it works even if the write-path holes are closed.

### Which entities have filters at all, and why Lead must not *(added 2026-08-25)*

Worth stating, because it looks like an oversight and is the opposite of one.

`app.jdl:202` declares `filter Client, Project, Ticket, Quote, ServiceItem, Course`. **`Lead`, `TeamMember`, `Milestone` and `QuoteLine` are absent**, so they have no `Criteria` class, no `QueryService`, and no `/count` endpoint. `GET /api/leads/count` is not a miss — `count` is parsed as an `{id}` path variable and answers 400.

The consequence surprises people, so it is worth being precise about what it is: a criteria-shaped parameter on an unfiltered resource is simply an *unknown* parameter, and Spring ignores unknown query parameters everywhere. `GET /api/leads?email.equals=nobody@example.com` returns every lead — but so does `GET /api/clients?banana=1` on a resource that *is* filterable. Verified on the quality stack:

| Request | `X-Total-Count` |
|---|---|
| `/api/clients` | 1 |
| `/api/clients?name.equals=Filter Probe Ltd` | 1 — the filter matches |
| `/api/clients?name.equals=nobody` | 0 — the filter excludes |
| `/api/clients?banana=1` | 1 — unknown parameter ignored |
| `/api/leads?email.equals=…` | all of them — `email.equals` is unknown here, exactly like `banana` above |

So there is nothing to fix in `LeadResource`. What matters is the opposite question — whether to *add* filtering for parity with its siblings — and the answer is no.

**Lead is the one table in this application holding third-party personal data collected without consent from a form anyone on the internet can reach.** Everything above in this finding describes what filters plus a count endpoint do to a table: they turn it into a blind extraction oracle, recoverable character by character with `contains`, figure by figure with `greaterThan`. The staff-only rule in `SecurityConfiguration` is an authorization boundary; it is not a defence against a staff account that has been phished, and the oracle is exactly what makes such an account maximally useful to whoever holds it.

Leaving `Lead` out of `filter` denies that oracle on the most sensitive table in the schema. If a future JDL change adds it — for a CMS screen that wants to search the pipeline, say — the search should be a deliberate, narrow endpoint that returns what an operator needs, not the generic criteria surface with `/count` beside it.

**Remediation.** Extract the scoping block into a private helper and call it from *both* the list and the count handler:

```java
private void applyClientScope(ProjectCriteria criteria) {
    if (!portalSecurity.isStaff()) {
        LongFilter clientScope = new LongFilter();
        clientScope.setEquals(portalSecurity.requiredClientScope());
        criteria.setClientId(clientScope);   // overwrite, never merge
    }
}
```

Overwriting rather than merging matters: `setClientId` must clobber any caller-supplied `clientId` filter, which the current code does correctly — preserve that property in the helper.

### SEC-04 — No brute-force protection; 4-character passwords *(High)*

**Where:** `SecurityConfiguration.java:71` (login is `permitAll`) · `ManagedUserVM.java:11` · `LoginVM.java:16`

- `POST /api/authenticate` has no rate limit, no lockout, no throttle, no CAPTCHA. Nothing in the codebase implements one — `grep` for rate/bucket4j/lockout/attempt across `src/main/java` returns no hits. nginx adds none either (SEC-07).
- `PASSWORD_MIN_LENGTH = 4` (`ManagedUserVM.java:11`) and `LoginVM` accepts `@Size(min = 4)`. A four-character password is exhaustible in seconds against an unthrottled endpoint.
- No MFA on `/api/register`-created staff accounts, which hold `ROLE_ADMIN` over the whole CMS.

Mitigating: `ANKOBRA_ADMIN_PASSWORD` is generated by `openssl rand -base64 24` during bootstrap, so the seeded `admin` account itself has a strong password, and `/api/register` is admin-gated (`SecurityConfiguration.java:75`) so attackers cannot self-register. The exposure is against accounts an admin creates for clients and consultants, whose passwords are whatever the admin chooses — with a floor of four characters.

**Remediation.**

1. Raise `PASSWORD_MIN_LENGTH` to 12 and add a breach-list check (`zxcvbn` client-side, or a HIBP k-anonymity range query server-side). Note that raising it does not invalidate existing weak passwords — force a reset for any account created before the change.

   **Both closed, 2026-08-24.**

   *Breach check.* `BreachedPasswordChecker` queries HIBP's k-anonymous range API on every password
   set — register, change, and reset-by-key. Only the first five hex characters of the SHA-1 leave the
   process, and `Add-Padding: true` makes the response a uniform size, so neither the password nor its
   length is observable. (The SHA-1 is the API's lookup key, not a credential hash; storage is still
   bcrypt. It is exempted in `.github/codeql-allowlist.txt` with that reasoning, rather than suppressed
   inline where nobody would find it.)

   It **fails open**: a timeout, DNS failure or HIBP outage lets the password through. Deliberate, and
   recorded in §2.1 — failing closed would let a third party's outage block password resets and account
   creation here, which trades a partial control for the availability of account recovery, the thing
   people need most when something has already gone wrong. Fail-open is only defensible if it is
   visible, so every failure increments `ankobra.password.breach_check{outcome="unavailable"}` and
   writes an audit line; a silent fail-open is indistinguishable from a check that passes. Bounded by a
   2s timeout, because an unbounded wait is neither open nor closed. Disabled in the test profile: a
   suite that depends on a third party being reachable is flaky, and worse, one that fails open would
   pass for the wrong reason.

   *Forced reset.* `jhi_user.must_change_password`, set by migration for every account that predates
   the policy. Bcrypt hashes carry no length, so there is no way to ask which stored passwords would
   fail today's rules — the accounts that existed before the rules did is the only answer available.
   `admin` is excluded: its password is machine-generated by `infra.sh` and rewritten from
   `ANKOBRA_ADMIN_PASSWORD` at every boot, so forcing a change there would be undone by the next
   restart and would leave the one account that can fix things locked to the password screen. The
   changeset is `context="prod"`, like the SEC-16 removal, so it does not flag the seeded `user`
   account that dev and test rely on.

   Enforcement is `PasswordChangeRequiredFilter`, last in the chain so it can only ever narrow what a
   session reaches: a flagged account gets `/api/account` and `/api/account/change-password` and
   nothing else, with a distinct problem type so the client can send the user somewhere useful instead
   of showing a dead end. Refusing to *authenticate* would have been the obvious design and does not
   work — changing a password requires being authenticated, so it would leave the user unable to comply.
   `POST /api/admin/users/{login}/require-password-change` sets the flag on demand; like
   `revoke-sessions`, it must go through `UserService`, because `findOneByLogin` is `@Cacheable` and a
   raw SQL update stays invisible for the cache TTL.
2. Add per-IP **and** per-username throttling on `/api/authenticate`. Cheapest correct option given the stack: a Bucket4j filter in front of the auth endpoint, keyed on both, with exponential backoff. An nginx `limit_req` zone (SEC-07) is a useful second layer but is IP-only and so is weak against distributed guessing.
3. Add progressive account lockout with an audit trail (see G-04).

### SEC-06 — XSS-to-account-takeover chain *(Medium — three of four links broken; see status below)*

**Status 2026-08-06.** The chain the audit described was: an XSS reads the token from `localStorage`, and the stolen token is admin-capable, long-lived and unrevocable. Three of those four links are now broken:

| Link in the chain | Then | Now |
|---|---|---|
| CSP lets injected script run | `'unsafe-inline'` + `'unsafe-eval'` + a public bucket as a script source | **`script-src 'self'`** — no inline, no eval, no third-party host |
| Token is long-lived | 30 days with remember-me | 7 days |
| Token cannot be revoked | only by rotating the key, signing out everyone | **per-user revocation** (SEC-09), instant, one account |
| Token is readable by script | `localStorage` | **unchanged** |
| Injected `<style>` can restyle the page | `style-src 'unsafe-inline'` | **per-response nonce** — an injected `<style>` carries no nonce and does not apply |

**Status 2026-08-24 — both remaining items closed.** The two gaps below are fixed, and the chain the
audit described has no links left:

| Link in the chain | Then | Now |
|---|---|---|
| CSP lets injected script run | `'unsafe-inline'` + `'unsafe-eval'` + a public bucket | `script-src 'self'` |
| Injected `<style>` applies | `style-src 'unsafe-inline'` | per-response nonce |
| Injected `style="…"` applies | `style-src-attr 'unsafe-inline'` | **directive removed** — all 43 attributes are classes |
| Token readable by script | `localStorage` | **`HttpOnly` cookie** — `document.cookie` shows only `XSRF-TOKEN` |
| Token is long-lived | 30 days | 7 days |
| Token cannot be revoked | key rotation only | per-user, instant (SEC-09) |

**One finding came out of doing it, and it is the important part of this entry — see
"The CSRF exemption that was not obvious" below.**

**What was still open before 2026-08-24:**

1. **`style-src-attr 'unsafe-inline'`** — reduced, not closed. The nonce work shipped: `CspNonceFilter` mints a value per response, `SpaWebFilter` renders the shell rather than forwarding so it can stamp `ngCspNonce`, and `style-src` now accepts only that nonce. An injected `<style>` block — the dangerous form, able to restyle or overlay everything already on the page — no longer applies. What remains is `style-src-attr`, because a nonce cannot cover `style="…"` attributes and the app has 43 of them (9 in the shell, 34 bespoke one-offs in portal and CMS templates). Removing them is a markup refactor rather than a security control, and it buys little: an attribute styles only the element it sits on, and with every fetch directive at `'self'` CSS cannot exfiltrate anywhere regardless.
2. **The token is still in web storage.** Moving it to an `HttpOnly` cookie remains the textbook answer, but the cost/benefit has shifted since this was written: it requires reinstating the CSRF protection `SecurityConfiguration` currently disables on the strength of the bearer-token design, across every mutating endpoint including an anonymous one (the contact form) and the login POST itself. Meanwhile the *consequence* it guards against has shrunk — a stolen token now dies in one API call instead of surviving a month. And with `'unsafe-inline'` still on `style-src`, an XSS that did occur could ride the session from inside the page regardless of where the token is kept. **Recommendation: do the nonce work first** — it closes the remaining execution surface and makes the cookie question mostly moot — rather than taking on a CSRF migration for a threat whose blast radius is now measured in minutes.

### What shipped, 2026-08-24

**1. The 43 inline style attributes are gone, and `style-src-attr` with them.** They became classes —
mostly in `global.scss`'s `.pview` block (`.pgrid-*`, `.pcard-*`, `.pt-*`), plus `quotes.scss` for the
line-item column widths and `home.scss` for the terminal's window-control dots. The shell's nine moved
into `content/css/loading.css`, and `loading-error.js` now toggles a class rather than assigning to
`element.style.display` — CSP does not police CSSOM writes, but relying on that distinction to keep a
control working is how controls quietly stop working. The policy is now free of `'unsafe-inline'`
entirely.

Because a stray `style="…"` would now be *silently ignored by the browser* rather than merely
inelegant — the element renders unstyled and nothing errors — `ContentSecurityPolicyConfigTest` grew a
sweep over every template in `src/main/webapp`. Verified in a browser as well as in tests: catalogue,
team, training, projects, clients, quotes and the overview all render correctly, with no CSP
violations in the console.

**2. The token is in an `HttpOnly` cookie, and CSRF protection is on.** `AccessTokenCookie` issues it
`HttpOnly; SameSite=Strict; Path=/`, `Secure` when the request is HTTPS (always true behind the
production proxy; never true in local dev, where a `Secure` cookie would simply be dropped).
Remember-me becomes a persistent cookie, a plain login a session cookie — the distinction
localStorage-vs-sessionStorage used to express. The login response now carries the token *nowhere* a
client can read: not in the body, not in a header. Logout became a server call (`POST /api/logout`),
because script cannot delete an `HttpOnly` cookie — which is the same property that makes it worth
having.

CSRF is the double-submit cookie: Spring writes `XSRF-TOKEN`, requires `X-XSRF-TOKEN` back. Those are
Angular `HttpClient`'s defaults, so the client needed no code for it. Two details that are not
optional: the token must be issued **eagerly** (`setCsrfRequestAttributeName(null)`), or the cookie is
never written for an SPA and every write fails forever; and the anonymous contact form is deliberately
**not** exempt — a uniform rule is one fewer exemption to reason about.

Verified in a browser on the final build: login `200`, `/api/account` `200`, `document.cookie` shows
only `XSRF-TOKEN`, `localStorage` empty.

### The CSRF exemption that was not obvious

The first implementation read the cookie in a custom `BearerTokenResolver`. That is the shape the
framework invites, and it **silently disabled CSRF protection for every authenticated request.**

`OAuth2ResourceServerConfigurer` registers a CSRF override: any request its bearer-token resolver can
read a token from is added to `csrf().ignoringRequestMatchers(...)`. The reasoning is sound for the
case it was written for — a token in an `Authorization` header must be attached deliberately by
script, and a browser will never attach one to a cross-site request, so CSRF cannot apply. A token in
a *cookie* is the exact opposite: the browser attaches it to every request to this origin, including
ones a hostile page provokes. Feeding a cookie to the resolver converts a correct optimisation into a
complete bypass of the protection the whole migration depends on.

Measured against the running application, not inferred:

| Request | With cookie resolver | After the fix |
|---|---|---|
| `POST /api/tickets`, no session, no CSRF token | 403 | 403 |
| `POST /api/tickets`, **valid session**, no CSRF token | **400 — reached the controller** | **403** |
| `POST /api/tickets`, **valid session**, deliberately wrong token | **400 — reached the controller** | **403** |
| `POST /api/tickets`, valid session, matching token pair | 400 (validation) | 400 (validation) |
| `GET /api/account`, valid session | 200 | 200 |

**Every test passed throughout.** They passed because a MockMvc test that omits the CSRF token also
omits the session cookie, so it never entered the exempted state — the suite only ever exercised
unauthenticated forgery, which is not the threat. `CsrfProtectionIT` now logs in for real and replays
the request with the session and without the token; that case fails against the resolver
implementation and is the guard.

The fix is `CookieAccessTokenFilter`, registered **after `CsrfFilter`**: at the moment the CSRF check
runs the request has no `Authorization` header, so nothing is exempted and the check happens; the
header is added immediately afterwards, in time for `BearerTokenAuthenticationFilter`. Ordering is the
entire mechanism, and it is stated at the registration site as well as in the class.

**The general lesson worth keeping:** a security control moved from one transport to another does not
carry its framework's assumptions with it. The exemption was correct for headers and catastrophic for
cookies, and nothing in the type system, the configuration, or 583 passing tests said so — only a
request made against a running server did.

### Two things noticed while verifying, neither introduced here

- **The portal's "Exit" button never logged anyone out.** `portal.html:46` is
  `routerLink="/"` — it returns to the marketing site and leaves the session live. `portal.ts:105`
  has a `logout()` method that no template calls. Pre-existing, but it matters more now: a user who
  clicks it expecting to sign out leaves behind a session in a cookie they cannot clear themselves.
  Not fixed here because it is a UX decision (is "Exit" meant to sign out, or to visit the public
  site?), not a security fix to make unilaterally.
- **The test database is file-backed and survives between runs** (`target/h2db/testdb`, from
  `application-testdev.yml`). A row committed by a failing test stayed there and failed
  *different* tests on the next run, with a message pointing nowhere near the cause. `rm -rf
  target/h2db/testdb` resolves it; worth knowing before debugging a mysterious suite failure.

*Original finding:*

Three weaknesses compose:

1. **Token in web storage.** `state-storage.service.ts:28,35` writes the JWT to `localStorage` (rememberMe) or `sessionStorage`. Any script executing in the page origin can read it.
2. **CSP permits inline and eval'd script.** `application.yml:237`:
   `script-src 'self' 'unsafe-inline' 'unsafe-eval' https://storage.googleapis.com`
   `'unsafe-inline'` removes CSP's principal defence against injected script, so the policy provides no meaningful XSS mitigation. `https://storage.googleapis.com` — a bucket host anyone can publish to — is a script source; nothing in this app appears to load script from it.
3. **Long-lived, non-revocable tokens.** 24 hours, or 30 days with rememberMe (`application-prod.yml:99-102`). See SEC-09.

Net: one XSS (e.g. via SEC-05, in a CMS view rendering a public `Lead.message`) yields an admin JWT valid for up to 30 days that cannot be revoked without rotating the signing secret and logging out every user.

**Remediation.**

- Remove `'unsafe-eval'` (Angular AOT production builds do not need it) and drop `https://storage.googleapis.com` unless something genuinely loads from it. Removing `'unsafe-inline'` requires nonce/hash-based styles and scripts — worth scheduling, but the first two are free.
- Prefer an `HttpOnly; Secure; SameSite=Strict` cookie over web storage for the token. This is a larger change (JHipster's JWT client assumes a bearer header, and it reintroduces the CSRF requirement that `SecurityConfiguration.java:47` currently disables on the strength of the bearer-token design) — treat as a deliberate follow-up, not a quick fix.
- Shorten `token-validity-in-seconds-for-remember-me` from 30 days; 7 is a defensible compromise.

### SEC-14 — Security headers never reach the SPA entry point *(High — found 2026-08-05 while verifying SEC-06, NOT yet fixed)*

**Where:** `web/filter/SpaWebFilter.java:28` · `config/SecurityConfiguration.java:48`

Every security header the app configures — CSP, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` — is **absent from `GET /`**, the URL every visitor actually loads. Verified against production immediately after the P1 deploy:

```
$ curl -sI https://jojoaddison.net/            | grep -ci content-security-policy
0
$ curl -sI https://jojoaddison.net/index.html  | grep -ci content-security-policy
1
```

Both URLs traverse the same nginx `location /` block, so this is the application, not the edge. `SpaWebFilter` forwards any non-API path to `/index.html` (`SpaWebFilter.java:28`), and the Spring Security filter chain — which includes `HeaderWriterFilter` — is not applied to `FORWARD` dispatches. The forwarded response is therefore written without the headers.

**Impact.** The headers are present only where they matter least. API responses are JSON consumed by `fetch`; the HTML document that loads and executes the application's JavaScript has no CSP, and can be framed despite `X-Frame-Options: SAMEORIGIN`. This substantially undercuts SEC-06: tightening the policy is worth little while the policy does not reach the page. It also predates this audit — it is generator-default behaviour, not a regression.

**Cause.** `HeaderWriterFilter` writes its headers when the response *commits*, not when the filter runs. `SpaWebFilter` forwards the request to `/index.html`, and in the packaged application the forwarded response is committed by static-resource handling without the filter's commit hook firing — so the headers are never written.

**The obvious fix does not work.** Adding `forward` to `spring.security.filter.dispatcher-types` was tried first and deployed; `GET /` was still bare afterwards. The property is valid in Boot 4 (it is in `spring-boot-security-4.0.6`'s metadata), but it cannot help here: **every filter in the chain extends `OncePerRequestFilter`**, so on the forward dispatch they all see the already-filtered request attribute and skip — `HeaderWriterFilter` included. Recorded because it is the answer most searches will offer.

**Remediation — applied and verified.** Make the filter write eagerly, so the headers land on the response *before* the forward. They survive it because `RequestDispatcher.forward()` clears the buffer, not the headers:

```java
.headers(headers -> headers
    .withObjectPostProcessor(new ObjectPostProcessor<HeaderWriterFilter>() {
        @Override public <O extends HeaderWriterFilter> O postProcess(O filter) {
            filter.setShouldWriteHeadersEagerly(true);
            return filter;
        }
    })
    ...
)
```

**How it was verified.** Not by the test suite — `SpaSecurityHeadersIT` passes either way, because the embedded server resolves the SPA from `src/main/webapp` as a Tomcat docBase while the packaged app serves it from the classpath. Instead: the production jar was built and run locally **under the `prod` profile** against a throwaway PostgreSQL, and `GET /` returned CSP, `X-Frame-Options` and `X-Content-Type-Options`. The negative control is production itself — image `23599aa`, same profile, same packaging, queried directly on `127.0.0.1:8090` to bypass nginx, returned none of them. The two runs differ only by this post-processor.

**Consequence that had to be fixed with it — HSTS.** Once the headers actually reached `/`, Spring Security's *own* HSTS writer appeared alongside nginx's: `max-age=31536000 ; includeSubDomains`. It had been firing on API responses since `e7416a9` made `request.isSecure()` true behind the proxy, and this change extended it to the most-visited path on the site. `includeSubDomains` asserts HTTPS-only for **every** `*.jojoaddison.net` subdomain for a year — and `https://web.jojoaddison.net` does not currently answer at all, so any browser that visited the apex would then refuse to reach it over HTTP. Exactly the outcome SEC-07 deliberately avoided. The app's writer is now disabled (`.httpStrictTransportSecurity(HstsConfig::disable)`) and nginx is the single source of the transport policy; that also removes the duplicate header, which RFC 6797 leaves the user agent to disambiguate.

**Also worth knowing:** the discarded `dispatcher-types` attempt must go inside the **existing** `spring.security` block. A second `spring.security:` key in one YAML document makes Boot's strict loader fail the whole context with "found duplicate key" — which is how the first attempt broke every integration test at once.

The discarded change, for the record:

```yaml
spring:
  security:
    filter:
      dispatcher-types: async,error,forward,request   # default omits `forward`
```

`SpaWebFilter` extends `OncePerRequestFilter`, so it will not re-enter and re-forward; `/index.html` is already `permitAll`, so re-running authorization on the forwarded dispatch changes no access decision. Confirm after deploying with `curl -sI https://jojoaddison.net/ | grep -i content-security-policy`, and confirm the app still loads.

### SEC-07 — Missing transport and edge hardening *(Medium)*

**Where:** `deploy/prod-server/ankobra-web.conf`

Absent from the TLS server block:

| Control | Consequence |
|---|---|
| `Strict-Transport-Security` | No HSTS. First-visit and any `http://` link is downgrade-attackable despite the 301 at `ankobra-web.conf:74-80`. |
| `server_tokens off` | Responses advertise `nginx/1.24.0 (Ubuntu)` — confirmed live. Free version intel for an attacker. |
| `client_max_body_size` | Defaults to 1 MB; explicit is better, and the app has no larger legitimate upload. |
| `limit_req` on `/api/authenticate` | No edge rate limit; see SEC-04. |

**Remediation** in the `443` server block:

```nginx
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
server_tokens off;
client_max_body_size 1m;

limit_req_zone $binary_remote_addr zone=login:10m rate=5r/m;   # http{} scope
location = /api/authenticate {
    limit_req zone=login burst=5 nodelay;
    proxy_pass http://127.0.0.1:8090;
    # ... same proxy_set_header block as location /
}
```

Do **not** add `preload` to HSTS until you are certain every current and future subdomain of `jojoaddison.net` is HTTPS-only — this host also serves `web.`, `portainer.` and `monitoring.` subdomains from a separate config, and `includeSubDomains` covers them too. Verify those first, or drop `includeSubDomains`.

*2026-08-24:* the verification was done (§2.1) and `includeSubDomains` is now on. `preload` is still deliberately absent — `includeSubDomains` binds only browsers that have visited this origin and expires in a year; `preload` binds every browser, indefinitely, and removal from the list is slow and not in this project's control.

Note the `add_header` inheritance rule: `add_header` in a `location` block discards all inherited `add_header` directives from the server block. The existing `location ~* \.(js|css|…)$` block at `ankobra-web.conf:56-61` sets `Cache-Control`, so once HSTS is added at server level, that location will silently lose it. Repeat the HSTS header there, or use the `always` flag together with a header module that merges.

### SEC-08 — Public enquiry endpoint has no anti-automation *(Medium)*

**Where:** `PublicEnquiryResource.java:45-64`

`POST /api/public/enquiries` is `permitAll` and writes a `Lead` row per call, with no rate limit, CAPTCHA, honeypot field, or proof-of-work. Field-level validation caps individual sizes (120/160/40/2000 chars) but nothing caps call volume. An anonymous caller can insert rows at request rate, filling the database volume, drowning the sales pipeline in spam, and — because each call also increments a Micrometer counter and emits a 100%-sampled trace in production (`compose.yml:93-95`) — inflating the metrics and tracing backends too.

Positive notes: the payload is a narrow record that never trusts client-supplied `status` (correctly commented at `PublicEnquiryResource.java:77`), `parseNeed` fails closed to `OTHER` on an unknown enum so the metric tag cardinality stays bounded, and the `LOG.debug` of the submitter's email (`:48`) does not fire in production, where the level is INFO (`application-prod.yml:16-20`).

**Remediation.** Per-IP rate limit at nginx (same `limit_req` mechanism as SEC-07, a separate zone at something like 3r/m), plus a honeypot field the real form leaves empty and the server rejects when filled. A CAPTCHA is a heavier UX cost; consider it only if abuse actually materialises.

### SEC-09 — No server-side session revocation *(Medium — fixed 2026-08-05)*

**Fixed.** `jhi_user.token_version` is stamped into every token as a `tv` claim, and `TokenVersionValidator` rejects any token issued before the user's current generation. It is registered *alongside* `JwtValidators.createDefault()` via `DelegatingOAuth2TokenValidator`, not in place of it — replacing the defaults would have traded a revocation hole for a missing expiry check. Revocation fires on password change, password reset, the active→inactive transition of an admin edit, and an explicit `POST /api/admin/users/{login}/revoke-sessions`. A deleted account's tokens stop working because the subject no longer resolves.

Two decisions worth knowing:

- **A missing `tv` claim reads as generation 0**, so tokens issued before this shipped survive the deploy rather than an upgrade signing every user out. The first bump for a user still kills theirs immediately.
- **The comparison is `<`, not `!=`.** A token *ahead* of the row can only mean the version went backwards — a restore from backup — and signing someone out over a rolled-back database achieves nothing.

**The cache is part of the security contract here.** `findOneByLogin` is `@Cacheable` and the validator reads through it, so a revocation that does not evict is silently ineffective for the cache TTL — an hour in production. `UserService.revokeSessions` evicts; a raw SQL `UPDATE` does not, and needs an application restart. `TokenRevocationIT` caught this: revoking and then logging in again produced a token that was rejected on arrival, because the fresh login minted it from a stale cached version. The runbook now carries that warning.

*Original finding:*

Logout is entirely client-side — `auth-jwt.service.ts:32-37` clears storage and completes. Stateless JWT means a copied token stays valid until it expires: up to 24 hours, or 30 days with rememberMe. There is no denylist, no `jti` tracking, no per-user token version. Consequences: firing a consultant does not end their session; a stolen token (SEC-06) cannot be killed; the only revocation available is rotating `JWT_BASE64_SECRET`, which signs *everyone* out — correctly documented as the intended response to a suspected leak in `.env.example`, but far too blunt for routine offboarding.

**Remediation.** Add a `tokenVersion` column to `User`, embed it as a claim at issuance, and compare it during validation; bumping the user's version invalidates only their tokens. Cheaper interim step: shorten the remember-me validity (SEC-06) to bound the window.

### SEC-16 — Default credentials were live in production *(High — found and fixed 2026-08-06)*

**Where:** JHipster's initial Liquibase changelog (`users.csv`), which seeds `admin` and `user`.

`AdminPasswordInitializer` rewrites the seeded **`admin`** password at every boot from
`ANKOBRA_ADMIN_PASSWORD`, and the audit recorded that as closing the `admin`/`admin` hole. It only ever
touched `admin`. The second seeded account — login **`user`**, JHipster's stock demo account — kept the
password from the changelog, was `activated = true`, and held `ROLE_USER`.

**Confirmed exploitable, not inferred.** A single request against production:

```
POST /api/authenticate  {"username":"user","password":"user"}   ->  HTTP 200
```

A working portal session, available to anyone who has ever seen a JHipster application. No brute force
needed, so the SEC-04 throttle would not have noticed; it is a correct password.

**Impact.** `ROLE_USER` is the client role, so under the authorization model as it now stands this
account could read whatever client record it was linked to — nothing, since it was linked to none.
**Before the SEC-01/SEC-02 fixes earlier the same day, this account could have deleted every client,
project and ticket in the database, and read every captured lead.** For the entire life of the
deployment up to that point, the cross-tenant write holes were reachable by an anonymous member of the
public with a guessable password, not merely by a client who had been issued one. That reframes the
severity of SEC-01 and SEC-02: their exploitability was never gated on a client account existing.

**Fixed.** Deleted through `DELETE /api/admin/users/user` rather than SQL, so the cache eviction and
the `event=account.deleted` audit record both fired. `user`/`user` now returns 401.

**The lesson is about the shape of the earlier fix.** `AdminPasswordInitializer` solved the instance of
the problem that had been noticed instead of the class. A guard that asserted *no seeded account
retains a changelog password* would have caught this; one that rewrites a hard-coded login could not.
Worth adding before the next generator upgrade reintroduces a demo account.

### SEC-15 — The database had never been backed up *(High — found 2026-08-05 while implementing SEC-10, now fixed)*

**Where:** root's crontab on the server · `deploy/README.md`

SEC-10 below assumed backups existed and criticised their encryption and retention. They did not exist. `backup.sh` was written, deployed to the host by `deploy.sh`, and documented — but the crontab entry the README told the operator to add by hand was never added. `~/webroot/01-jojoaddison/ankobra-web/backups/` did not exist, and no dump had ever been taken. Production was one disk failure from total, unrecoverable data loss, for the entire life of the deployment.

This is what a manual step in a README looks like after a few weeks. The script's own quality was never the problem; nothing ran it.

**Fixed 2026-08-05.** Nightly backup and weekly restore drill are in root's crontab, added idempotently so the sibling apps' entries were preserved (verified: the pre-existing crowdfunding entry survived, 10 active entries). A first backup has been taken and a first restore drill has passed against production.

**Lesson worth keeping:** treat "add this to crontab" in a README as an outage waiting to happen. Anything the system genuinely depends on either ships as code or gets verified by something that fails loudly.

### SEC-10 — Backups unencrypted and single-host *(Low)*

**Where:** `deploy/prod-server/backup.sh`

`pg_dump` output is written to `backups/` with `chmod 700` on the directory and `600` on the file, 14-day retention. Good hygiene, but the dumps are **plaintext**, stay **on the same host as the database**, and contain every `Lead` row — third-party names, emails and free-text messages. A host compromise takes both the live data and its history; a host loss takes the backups with it.

**Remediation.** Encrypt at rest (`age` or `gpg --encrypt` to a public key whose private half lives off-host), ship off-host, and add a periodic restore test (G-05). An unverified backup is a hypothesis.

### SEC-11 — Metrics endpoint open on a shared network *(Low — assessed 2026-08-05, accepted)*

**Assessed and accepted, with the trigger that would reopen it.** Re-checked against production:

- Every `/management/*` path — `prometheus`, `health`, `env`, `configprops` — returns **404 publicly**. nginx blocks the prefix, so none of this is internet-reachable.
- `/management/prometheus` does answer **200 unauthenticated** on the container network.
- The shared `monitoring` network holds ~15 containers, and they are **not all monitoring infrastructure**: alongside `otel-collector`, `tempo`, `mimir` and the exporters sit sibling *applications* — `kojo-stack-api`, `abofonsa-api`, `hc-patient-service`, `hc_crowdfunding_api`. Any of them could scrape this app's metrics.

**Accepted because** what they would get is request counts, latencies, URI *templates*, JVM internals and the `ankobra.enquiries.submitted` counter — no PII, no secrets, no request contents. The counter's only tag is `need`, and `parseNeed` maps anything unrecognised to `OTHER`, so a caller cannot inject an unbounded or personal value into a label. Closing it would mean putting authentication on the scrape endpoint and editing the shared Prometheus configuration, which belongs to a different stack on this host.

**What would change the decision:** any metric that gains a tag carrying user-supplied or personal data — a client name, an email, a login, a raw URI. At that point the exposure stops being counts and starts being data, and the scrape endpoint needs authentication regardless of whose config has to change.

*Original finding:*

`SecurityConfiguration.java:86` makes `/management/prometheus` `permitAll`, and `compose.yml:78-81` joins the app to the **external, shared** `monitoring` network so Prometheus can scrape it. Any other container on that network — from any other app on this host — can read the app's metrics: endpoint URIs, request counts and latencies, JVM internals, and the `ankobra.enquiries.submitted` business counter. `/management/**` is otherwise ADMIN-gated (`:87`) and nginx 404s the whole prefix publicly (`ankobra-web.conf:66-68`), so this is not internet-exposed.

Low severity, and largely inherent to a shared monitoring network. Worth knowing it is a cross-tenant boundary, and worth confirming that the other tenants on `monitoring` are all trusted. `/management/health/**` is also `permitAll` (`:83-84`) but `show-details: when_authorized` with `roles: ROLE_ADMIN` (`application.yml:47-48`) keeps the detail closed — correct as-is.

### SEC-12 — Working JWT secret committed to the repository *(Low)*

`src/main/resources/config/application-secret-samples.yml:20` contains a real 64-byte base64 HS512 key. It is a generator-shipped sample in a profile production never activates, and `.env.example` documents that production must supply its own or fail to start — both correct. The risk is purely that someone copies it into a live config. Consider replacing the value with an obvious placeholder (`REPLACE_ME_openssl_rand_base64_64`) so it cannot function if pasted.

### SEC-13 — Account lifecycle depends on unconfigured mail *(Low)*

`SMTP_HOST` defaults to empty (`compose.yml:79`, `.env.example`), documented as optional because the contact form only writes a DB row. But `/api/register` is admin-only (`SecurityConfiguration.java:75`), so **every** account is admin-created — and JHipster's admin-creation flow sends a creation/activation email. With no SMTP configured, that email never arrives. Meanwhile `/api/account/reset-password/init` is public and functional but equally silent, so a locked-out user has no self-service recovery.

The practical result is that account provisioning and recovery both depend on a channel that is off by default. Not a vulnerability, but it pushes operators toward insecure workarounds (setting passwords by hand, sharing them over chat).

**Remediation.** Configure SMTP, or document the intended out-of-band provisioning procedure explicitly. Password reset correctly avoids user enumeration (`AccountResource.java:144-153` returns success either way) — preserve that.

## 4. Gap analysis

Not vulnerabilities; missing coverage, controls and process.

### G-01 — The scoping test suite tests only what already works *(High)*

`PortalScopingIT` has five tests (`PortalScopingIT.java:95-126`): list-projects, list-tickets, get-project-by-id-denied, get-own-project-by-id, consultant-sees-all. **All five are GETs.** Not one asserts that a client cannot `DELETE`, `PUT`, `PATCH` or `POST` across the tenant boundary — precisely the holes in SEC-01.

This is worse than no tests: `CLAUDE.md` cites `PortalScopingIT` as proof that role scoping works, and it does prove that, for reads. The suite's green status is currently evidence for a claim broader than what it checks.

**Action.** For every entity × every verb, add a test asserting `403` for a cross-tenant client. Write them **before** the SEC-01 fix so they fail first and the fix is demonstrably what turns them green. A table-driven parameterised test over `(resource, verb)` will cover ~60 cases compactly and will fail loudly when a future JDL regeneration reintroduces an unguarded endpoint.

### G-02 — No dependency or image scanning in CI *(High)*

`.github/workflows/ci.yml` runs `./mvnw verify`, `npm test` and the prod webapp build. There is no `npm audit` gate, no OWASP dependency-check or equivalent for the Java tree, and no image scan (Trivy/Grype) on the jib output. SEC-05 has been live in `main` undetected as a direct consequence; the Java dependency posture is currently **unknown** for the same reason.

**Action.** Add to CI: `npm audit --omit=dev --audit-level=high` as a failing gate; a Java CVE scan (OWASP dependency-check, or Trivy in filesystem mode over the resolved dependency tree); and a Trivy scan of the published image in `publish.yml`. Enable Dependabot or Renovate for automated bumps.

### G-03 — No regression test for the CORS/forwarded-headers fix *(Medium)*

The SEC-00 fix is config-only, and no test exercises it — the same class of misconfiguration can regress silently on the next JDL regeneration, which rewrites `application-prod.yml`. `TracingAutoConfigurationIT` already sets the precedent of guarding custom prod config with a test.

**Action.** Add an integration test binding the prod `jhipster.cors` block and asserting `allowed-methods` includes POST; and a `MockMvc` test asserting `POST /api/authenticate` with an `Origin` header is not rejected by the CORS filter. Add both `application-prod.yml` blocks to the "re-apply after regeneration" list in `CLAUDE.md`, which currently names the tracing config but not these.

### SEC-17 — Credentials written to the application log *(Medium — found and fixed 2026-08-25 by the CodeQL gate)*

The first full-repository CodeQL scan on `main` — the gate added for G-06 — failed on
`java/sensitive-log` at `UserService.java:70`:

```java
public Optional<User> completePasswordReset(String newPassword, String key) {
    LOG.debug("Reset user password for reset key {}", key);
```

A reset key is a credential: whoever holds it can complete that account's password reset. This wrote
one to the application log on every attempt.

**Latent rather than live, which is the interesting part.** Production logs at INFO, so the line never
fired there — the same property §6 records as making the debug lines that print submitter email
addresses harmless. That is a configuration standing between a credential and a log file, not a
control: one `logging.level` change, or one `SPRING_PROFILES_ACTIVE` mistake, and live reset keys are
in Loki with whatever retention it has. Dev and quality logs contain them today.

It also directly contradicted an instruction already written in this codebase.
`SecurityAuditLogger`'s javadoc ends *"Never pass a password, token, or reset key to any method
here"* — written for the audit channel, while the service logger beside it did exactly that.

**Two siblings, found by reading rather than by the scanner.**

- `UserService.java:58` logged the **activation key** the same way. CodeQL did not flag it; an
  activation key is no less a credential, since it activates the account.
- `User.toString()` included `activationKey`, and `UserService` logs whole `User` objects in six
  places — `Activated user`, `Created Information for User`, `Changed Information for User`,
  `Deleted User`, and two more. So the key reached the log from paths that have nothing to do with
  activation. The password hash was already excluded, correctly; this field was not.

**Fixed.** Neither key is logged, and `activationKey` is out of `toString()`. That last one is a
divergence from what the generator emits, so it is on the regeneration checklist in `CLAUDE.md`.

**What this says about the gate.** G-06 was argued for on the grounds that a control nobody runs is
indistinguishable from no control. Its first full scan found a credential in a log line that had been
there since generation, that every test suite passed over, and that the audit itself had walked past
while writing the rule it broke.

### G-04 — No security audit logging *(Medium)*

`AbstractAuditingEntity` records created/modified-by on entities, and `SpringSecurityAuditorAware` populates it. But there is no log of authentication events: no successful-login record, no failed-attempt record, no record of admin actions like account creation or role change. `SecurityMetersService` counts invalid tokens as metrics only — aggregate counters, not attributable events.

After an incident there would be no way to answer "which account was used, from where, and what did it touch". This also blocks SEC-04's lockout, which needs failed-attempt state.

**Action.** Add an `AuthenticationSuccess`/`AuthenticationFailure` event listener writing structured log lines (login, source IP, outcome, timestamp), and log admin mutations to `User` and `Authority`. Logs already carry trace ids (`logback-spring.xml`) and ship to Loki, so the correlation infrastructure exists.

### G-05 — Backups are never restore-tested *(Medium)*

`backup.sh` refuses to keep an empty dump (a good check) but nothing ever verifies that a kept dump actually restores. Retention is 14 days, so a corruption introduced 15 days ago is unrecoverable and undetected.

**Action.** A scheduled job restoring the newest dump into a throwaway container and asserting row counts on key tables.

### G-06 — SAST configured but not enforced *(Low — fixed; see the correction below)*

`sonar-project.properties` and `checkstyle.xml` exist, but CI invokes neither. Whatever they would catch, they are not catching.

**Action.** Either wire Sonar into CI as a gate or remove the config so it stops implying coverage that does not exist. GitHub CodeQL is a zero-infrastructure alternative for both Java and TypeScript.

**Correction, 2026-08-24.** Two things in the finding as written are wrong, and the record should say so:

- **CodeQL already shipped**, in `82a0830`, along with a header on `sonar-project.properties` stating that it is not the gate. That went in as part of the P2 batch and was never written up here, which is how the item stayed open on paper after it had been done. A finding that is fixed but unrecorded is indistinguishable from one that is not.
- **checkstyle is invoked.** `maven-checkstyle-plugin` sits in `<build><plugins>` with a bound `check` goal, so `./mvnw verify` does run it. But its `<includes>` is `pom.xml,README.md` — it is JHipster's nohttp check, scanning two files for `http://` URLs, not a Java lint. The finding's claim that CI "invokes neither" was half true in a way that matters: the plugin runs and catches almost nothing, which is a worse failure mode than not running, because the build output says checkstyle passed.

**And Sonar cannot simply be deleted.** `properties-maven-plugin` is active in `<build><plugins>` and reads `sonar-project.properties` at the `initialize` phase (`pom.xml:362-365,704-716`). Removing the file breaks every Maven invocation, including `./mvnw verify`. Removing it properly means removing that plugin execution and `sonar-maven-plugin` too — all three of which JHipster re-adds on regeneration. Keeping the file with an explicit "this is not the gate" header is the cheaper honest option, and is what shipped.

**What was actually still open, and is now closed.** Publishing to the Security tab is not a gate. `github/codeql-action/analyze` raises alerts; whether an alert blocks a merge is a branch-protection setting in the repository's configuration, not in any file in the repository. So CodeQL was reporting, and nothing was failing. The workflow now writes the SARIF to disk (`output: sarif-results`) and fails the job on any finding whose rule carries `security-severity >= 7.0` — the same high/critical bar as `npm audit --audit-level=high` and the Trivy scan in `ci.yml`. The gate is visible in the code, survives a fork or a fresh clone, and does not depend on a setting nobody can see from the tree.

### G-07 — No documented incident response or key rotation runbook *(Low)*

`.env.example` documents that rotating `JWT_BASE64_SECRET` is the response to a suspected leak — the only such note anywhere. There is no runbook for: suspected account compromise, `POSTGRES_PASSWORD` rotation, revoking a departing consultant, or restoring from backup under pressure.

**Action.** A short `docs/runbook-security.md` covering those four, written before they are needed.

## 6. What was checked and found sound

Recorded so a future audit need not re-derive it, and so the report is not mistaken for a verdict on the whole system.

- **Container hardening is genuinely good.** `read_only: true`, `cap_drop: ALL`, `no-new-privileges:true`, non-root `<user>1000</user>` in the jib config (`pom.xml:651`), loopback-only published port, and Postgres publishing no port at all.
- **Secret handling is well designed.** All three production secrets are generated by `openssl rand` on the server during bootstrap and never touch the deploying machine or the wire. The app fails to start rather than falling back to a default — the right trade.
- **Production seeds no demo data.** `DataSeeder` is `@Profile("dev")` (`DataSeeder.java:58`); the `kojo`/`ama` demo logins with their published password cannot exist in production.
- **`admin`/`admin` is closed.** `AdminPasswordInitializer` rewrites the seeded account's password from `ANKOBRA_ADMIN_PASSWORD` at every boot, and compose makes the variable mandatory.
- **Self-registration is closed.** `/api/register` is ADMIN-gated (`SecurityConfiguration.java:75`) — a deliberate deviation from the JHipster default, correctly commented.
- **Password reset does not enumerate users** (`AccountResource.java:144-153`).
- **Actuator exposure is correctly gated** — `env`, `configprops`, `logfile`, `loggers` all require ADMIN; health detail is `when_authorized`; nginx 404s `/management` publicly.
- **Production logging is INFO**, so the debug lines that would print submitter email addresses never fire there.
- **`PublicEnquiryResource` takes a narrow record**, never binds the domain entity directly, and never trusts client-supplied `status` — mass-assignment is closed on the one endpoint anonymous users can reach.
- **`PublicUserResource` leaks little** — `UserDTO` carries only `id` and `login`, and the sort parameter is allowlisted against injection (`PublicUserResource.java:22-30,58-60`).
- **`PortalSecurityService` itself is correct**, including the `-1L` sentinel (`:41-43`) that makes an unlinked non-staff user match nothing rather than everything — the right failure direction. Its problem is under-application, not design.
- **JWT uses HS512 with a mandatory ≥64-byte key**; `SecurityMetersService` instruments invalid/expired/malformed tokens.
- **CI runs the full backend and frontend suites plus a production build** on every PR — good, as far as it goes (G-02, G-06).

### SEC-06 — proving the cookie and CSRF work, and that the exemption is closed

The matrix below is the one that caught the bypass. Run it against a *running* server: a MockMvc test
that omits the CSRF token also omits the session cookie, so it never reaches the interesting row.

```bash
B=https://jojoaddison.net    # or http://localhost:8099 in dev
curl -s -c jar.txt -o /dev/null "$B/"
X=$(grep XSRF-TOKEN jar.txt | awk '{print $7}')
curl -s -b jar.txt -c jar.txt -o /dev/null -X POST "$B/api/authenticate" \
  -H 'Content-Type: application/json' -H "X-XSRF-TOKEN: $X" \
  -d '{"username":"<login>","password":"<password>"}'

XSRF=$(grep XSRF-TOKEN jar.txt | awk '{print $7}')
ACCESS=$(grep ANKOBRA-ACCESS-TOKEN jar.txt | awk '{print $7}')
CJ="Cookie: XSRF-TOKEN=$XSRF; ANKOBRA-ACCESS-TOKEN=$ACCESS"
p() { curl -s -o /dev/null -w "%{http_code}\n" "$@"; }

# THE row that matters: a valid session, no CSRF token. 403. If this is 400 or 201, the
# resource server's bearer-token CSRF exemption is active and protection is off.
p -X POST "$B/api/tickets" -H 'Content-Type: application/json' -H "$CJ" -d '{}'
# A wrong token must be refused too, not merely a missing one. 403.
p -X POST "$B/api/tickets" -H 'Content-Type: application/json' -H "$CJ" -H 'X-XSRF-TOKEN: garbage' -d '{}'
# Matching pair reaches the controller (400 = bean validation on the empty body).
```
